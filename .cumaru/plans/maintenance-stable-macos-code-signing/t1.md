# T1 — Map the existing deployment integration

## What to do

Read the existing build and release configuration to locate where persistent signing belongs.
This is implementation preparation, not a test or a Keychain investigation gate.

## Context

The release workflow downloads a pinned Laufey build and uses it to assemble GoogleChatDeno.app.
The app includes the Laufey executable, helper applications, libraries, and CEF framework.
Our release signs the incorporated runtime as part of our app; the Laufey release pipeline stays intact.

## Implementation

1. Read build.sh, deno.json, and .github/workflows/release.yml for assembly, signing, and packaging order.
2. Record the current bundle identifier, runtime package layout, and nested-code signing order from
   the existing configuration and packaging sources; do not generate a prototype or test build.
3. Identify the existing workflow steps where production signing credentials will be imported,
   used, and removed.
4. Document the integration points for T2 and T3 without inspecting or changing user credentials.

## Done when

- [x] The existing assembly, signing, and packaging integration points are documented.
- [x] The incorporated Laufey runtime and our final application bundle are distinguished clearly.
- [x] No test builds, user-Keychain changes, or credential authorization experiments are required.

## Result

See [the T1 handoff](handoff-t1.md) for the source-backed deployment map and T2/T3 integration points.
